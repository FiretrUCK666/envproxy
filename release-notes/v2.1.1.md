# v2.1.1

这一版修三个问题，全部是 **v2.1.0 自己带进来的**。建议更新。

如果你还没更新到 v2.1.0，直接升到这一版就行，不用先升 v2.1.0。

---

# 问题一：断网时，工具会把一条死代理说成好的

v2.1.0 加了一条判断：一个检测网址的「通」，必须建立在「你不挂代理打不开它」之上。

但这条判断的实现有个漏洞：**它把「问不出来」和「确定被墙」当成了同一件事。**

具体表现：

- 你的 DNS 一时抽风（或者你用的客户端走加密 DNS，系统解析不出来）
- 你连着机场/酒店的登录页网络
- 你的网慢到超时

这三种情况下，六个检测网址全都会被判成「被墙了」——于是每一个都成了「合格证」。

结果就是：**一条对所有真网站都回 502 的死节点，只要肯对某个检测网址回一个 204，就会被判成「正在翻墙」，然后把这条死代理铺满你所有终端。** 屏幕全绿，终端全挂。

这正是 v2.1.0 想治的那个事故，只是触发条件从「两个 gstatic 域名」变成了「直连侧任何异常」。

## 现在怎么做

判断分成三档，而不是两档：

- **确定打不开**——解析得出、直连本身也上着网、但这个网站拿不到回应。**只有这一种能当证据。**
- **直连就能通**——证明不了代理。
- **问不出来**——DNS 失败、整条直连不通、拿到不该回的回应。**一律不算证据。**

第三档是关键：以前「不知道」被当成「被墙」，现在它老老实实是「不知道」。

# 问题二：判断会过期了

v2.1.0 把「这个网址在你这台机器上会不会被墙」的结论记了缓存，**而且永不清除**。

这意味着：开机那一瞬间网络还没起来，六个网址全判「被墙」，这个错误结论就**永久生效**。之后你换了节点、节点死了，工具照样报「正常」，直到你重启电脑。

## 现在怎么做

- 结论有**有效期**（10 分钟），到点重问
- 结论带**网络指纹**（默认网关 + 本机 IP）——换 Wi-Fi、插拔网线、开关 TUN、改分流规则，指纹一变就重问
- 「问不出来」不进缓存，下次再问

# 问题三：开 TUN 的用户，正常代理会被判成「没在翻墙」

如果你的代理软件开了 TUN（虚拟网卡接管全部流量），六个检测网址全都能「直连」打开——于是一个证据都没有，**一个正常工作的代理被判成「没在翻墙」**，而且不会自愈。

## 现在怎么做

六个全「直连可达」被认定为一个明确信号：**这套判据在你的机器上失效了**。

这时退回旧规矩（拿到回应就算通），并在日志里写一句：

```
本机所有检测网址不挂代理也能打开（多半是虚拟网卡接管了全部流量）-> 回到旧判据：经代理拿到回应就算通
```

反过来，六个全「问不出来」时**绝不退回**——那会让死节点靠随便一个 204 重新骗过判决。

# 顺带修的

- **mac 侧会挂死**：探测代码里有两次「等所有后台任务跑完」，等的是整个 shell 的任务，不只是自己的。线上碰不到（监控进程里只有探测），但任何人把它嵌进别的脚本都会被卡死。实测卡了 20 分钟。
- **两侧超时不一致**：mac 是 2 秒、Windows 是 2.5 秒。这个数是「直连算不算通」的分界线——同一个网站，Mac 说被墙、Windows 说直连可达，同一个代理被两台机器判成相反结论。统一到 2.5 秒。

# 自己查一下

想在更新前确认你遇到的是不是这个问题：

看程序目录下的 `monitor\monitor.log`（Windows）或 `~/.envproxy/monitor.log`（macOS）。
如果里面有「本机所有检测网址不挂代理也能打开」，说明判据在你的机器上本来就是降级状态。

# 已知边界

- **TUN 场景下这套判据不生效**：它会退回旧规矩，也就是说，「死节点被判活」这个风险在 TUN 场景下仍然存在。这是取舍：宁可回到旧行为，也不能把一个好代理判死。
- **慢网（3G、卫星、拥塞）下判定会变慢**：直连探测最多等 2.5 秒，六个网址全探一遍最坏约 15 秒。第一次判断会多花 2-3 秒，之后走缓存。
