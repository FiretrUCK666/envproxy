# v1.1.2

这一版修两件事：一件是「屏幕说已开启、实际连不上」，另一件是「明明在翻墙，工具却用了一个你看不见的端口」。

## 选端口：用软件自己声明的那个

**问题**：很多翻墙软件会同时开好几个端口。一个是你界面上看到的、它让你填进浏览器或系统代理的那个；另外还有几个是它内部进程之间通信用的，你在界面上永远看不到。

这两种口**都能翻墙、出口 IP 完全一样、握手也一样正常**，所以「这个端口能不能用」的判断一条都不会报错。区别只有一个：哪个是软件主动告诉操作系统的。

实测过一台 MonoCloud：界面上写 `10801`，系统代理里也是 `10801`，而它的内核另开了一个 `51081`。原来我们挑中了后者——用户在界面上看着 `10801`，工具报告 `51081`，自然会觉得「你搞错了」。

**修法**：任何翻墙软件要让浏览器走它的代理，就必须把对外那个端口写进系统代理。这是操作系统层面的约定，与软件叫什么、谁做的、哪个版本都无关。所以我们读系统代理，软件告诉系统用哪个，就用哪个。

同时加了纠错：端口一旦被选中就会被记住、此后每轮复用，先选错就永远错下去。现在每 10 轮复核一次「当前这个是不是软件声明的那个」，如果不是、而对方能通过握手和翻墙验证，就主动切过去。

**为什么不用「记住某个软件的端口」这种办法**：那样表里永远缺人。今天补 MonoCloud，明天还有别人的软件没补上。而「软件自己声明」是通则，环境怎么变都不会失效。

## 不再把自己的中继当成你的代理

**问题**：Windows 版有一个「固定入口」中继（默认 `127.0.0.1:17099`），它本身就是一个合格的代理。而探测逻辑完全不知道它的存在。

后果不是「多选了一个」，是**判反了**：

1. 你关掉翻墙软件，机器上只剩中继在监听
2. 兜底扫描命中它 → 判「已开启」→ 注入 `http://127.0.0.1:17099`
3. 而中继没有上游，所有终端工具（git / npm / curl）全部超时
4. 屏幕上却显示「一切正常」

比「不翻墙」更糟，因为你会以为它在工作。

**修法**：探测层读中继自己写下的端口记录（运行时值，端口被占用顺延时也能跟上），从四个来源统一排除。这是确定性判断，不增加任何网络开销。

实测反证过：去掉这条排除，候选集立刻就是 `17099`。

## 顺带修的一处性能问题

CI 里「sh 语法检查」这一条，原本要跑 **583 秒**。原因是它检查库之间有没有循环依赖时，写成了三层循环——12 个库 × 11 个库 × 平均 27 个函数，约 3600 次 `grep`，每次都要重读整个文件。

改成一次 `awk` 扫完，**降到 21 秒**，判据一个字没变（拿 update 库对比，新旧实现都是 11 条边，逐条一致）。

这个慢跟使用者无关（只在开发和 CI 里跑），但它拖慢了每次验证，间接让问题藏得更久。

## 已知边界

- 这一版没有新功能，用法与 v1.1.1 完全一样。
- macOS 侧没有中继，所以「排除自己的端口」只有 Windows 需要，代码里已标明原因。
- 如果某个翻墙软件**不**写系统代理（少数只开 TUN 的配置），我们退回到「常见端口表的顺序」。那时选到的端口可能不是最优，但一定是能用的——而那种情况下用户自己改了什么他心里有数。
