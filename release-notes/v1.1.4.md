# v1.1.4

这一版修的是「桌面上的『直连』图标在开着 TUN 时其实不管用，而屏幕上不说」。功能没有增减，用法与 v1.1.3 一样。

## 问题

「给程序建固定直连的图标」这个功能，原理是把代理设置从那个程序的环境里删掉，让它自己走直连。

它成立的前提是：**程序看不到代理地址，就不会翻墙。**

而 TUN 模式打破了这个前提。TUN 是一张虚拟网卡，工作在网络层——程序从来「看不到」它，它也不依赖任何环境变量。从程序的角度看，自己就是在正常联网，只是数据包在网卡那一层被抓走送进了隧道。

实测过：清空所有代理变量、用 `curl --noproxy '*'` 强制直连，访问 `google.com` 仍然返回 200，出口 IP 仍然是节点 IP。

**所以那个图标在 TUN 下做了等于没做，而屏幕还写着「一定不翻墙」。**

## 改了什么

**一、状态页多一行「流量走向」**

检测到网络层接管时，在「高级功能」下面显示：

```
流量走向 : 检测到 TUN / 全局 VPN 已接管全部流量（「直连」图标对它无效，其余照常）
```

用灰色、不报错。因为 TUN 本身完全正常，开了它反而是好事（全局生效）。它进的是说明，不是问题清单。

**二、建「直连」图标时，在按 y 之前先警告**

那一步是唯一的决策点。等建完才说，使用者会先建、用、发现没用、再回来删，三步都白做。

**三、把三处绝对化的承诺改准确**

「一定不翻墙」改成「照常上网，不经过翻墙线路。开着 TUN 时这条不成立。」

承诺落在它**能保证的那一步**上——「让程序看不到代理变量」这一步永远成立，「程序不翻墙」这个结果在有 TUN 时不成立。

## 判据为什么不写软件名

要回答的只有一个问题：**「程序看不到代理变量」还等不等于「程序不翻墙」？**

答案取决于流量分流发生在哪一层：应用层（靠环境变量）就成立，网络层（TUN、透明代理、全局 VPN）就不成立。

这个判断对 Global 模式、Smart 模式、任何厂家的翻墙软件一律适用，不需要为新的软件再写一遍。

**具体判据：本机有足够多条「覆盖公网」的宽路由。**

- 不看「有没有隧道网卡」：Tailscale 也是隧道网卡，但它只挂几条精确的单机路由（自己那几台机器），不接管公网。实测对照：MonoCloud 186 条公网宽路由，Tailscale 3 条且全是单机地址。
- 不看默认路由：规则模式（Smart）**不动默认路由**，它往隧道网卡上加几十到几百条网段路由做分流。只看默认路由会把最常见的模式整个漏掉。

阈值取 20：物理网卡通常 0-3 条，规则模式隧道几十到几百条，两边都远。

## 一个刻意不做的事

**不做「绕过 TUN 的直连」。** 技术上要靠进程级防火墙或路由表，那是杀毒软件级别的权限，而且会跟 TUN 抢路由，结果是随机断网。这个功能不该做。

## 已知边界

- 这一版没有新功能，用法与 v1.1.3 完全一样。
- 只影响「直连」图标：其余功能（代理变量注入、走代理的图标、终端同步）在 TUN 下照常有效，因为 TUN 和代理端口指向同一条隧道。
- 状态页那一行只在检测到接管时出现；读不到路由表时不显示——没有证据不给使用者加一行看不懂的警告。
